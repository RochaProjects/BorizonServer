# Server data preparation

`export-registry-sync.sh` creates the NBT data sent by the Minecraft 26.3 server during the configuration phase. It calls the exact `RegistrySynchronization` and `WorldLoader` implementations in `26.3-server.jar`; Rust does not infer NBT numeric types from JSON. It also writes `registry-order.json`: NBT compounds are maps, but vanilla assigns dynamic registry IDs from the ordered entry list, so the Rust loader requires and honors this explicit list.

The input is the **server jar** and its runtime libraries only. Do not pass a client jar or client asset directory.

```sh
tools/server-data/export-registry-sync.sh \
  /path/to/server-26.3.jar \
  /path/to/server-libraries \
  /path/to/resources
```

The command writes `resources/registry-sync/<namespace>/<registry path>.nbt`, `resources/registry-tags.nbt` and `resources/registry-order.json`. The engine loads registries and entries in vanilla's order and sends tag IDs generated by the same server jar. The resource directory also needs the block registry, behaviours and world-generation data expected by `horizon-engine`.

This is an offline preparation utility; it is not part of the engine runtime or Cargo dependency graph. It does not yet package the other server data, build a complete server bundle, or implement LOGIN/PLAY.

## Worldgen block behavior inputs

`export-worldgen-blocks.sh` generates the six block-property, collision, support and placement inputs required for vanilla FEATURES decoration. It compiles the Java exporters against the inner 26.3 server runtime jar from the official bundler and server runtime libraries; it does not use a client jar or Cargo's client crates.

```sh
tools/server-data/export-worldgen-blocks.sh \
  /path/to/26.3-server.jar \
  /path/to/server-libraries \
  /path/to/resources
```

The input resource directory must already contain `facts.json`, `worldgen/block_tags.json` and `worldgen/fluid_tags.json`. The script writes the six files under `resources/worldgen/blocks/`. It currently does not produce the rest of a complete server resource bundle.

## Root block registry and gameplay facts

`export-server-block-data.sh` creates `facts.json`, `block-behaviours.json`, `gameplay-facts.json` and `worldgen/block_flags.json` from the vanilla 26.3 server runtime. `facts.json` comes from the same server-side exporter used by the prepare pipeline, so its rows include the `air` and `fluid` columns consumed by Horizon. This script does not need client assets or client libraries.

```sh
tools/server-data/export-server-block-data.sh \
  /path/to/26.3-server.jar \
  /path/to/server-libraries \
  /path/to/resources
```

## Complete inputs for `horizon-engine`

`prepare-server-resources.sh` runs the server-only export steps in dependency order: vanilla worldgen JSON/templates and biome-parameter reports, root block registry/behavior/gameplay facts, synchronized protocol registries, and worldgen block-placement facts (including the root collision table and fluid-tag files needed by the loader). Point it at an empty or disposable output directory, then validate the result with `horizon-engine --validate-resources <directory>`.

```sh
tools/server-data/prepare-server-resources.sh \
  /path/to/26.3-server.jar \
  /path/to/server-libraries \
  /path/to/resources
```

This prepares engine inputs only. It does not produce a playable server binary: LOGIN is not wired into a TCP gameplay listener, PLAY needs complete lighting and a resident player/tick runtime, and persistence still needs to be driven by that runtime.

The preparation command also runs `net.minecraft.data.Main --server --reports` from the official server runtime and keeps only the Overworld/Nether `biome_parameters` reports needed by Horizon's generator. It discards the generator's temporary output after copying those two server worldgen reports.
